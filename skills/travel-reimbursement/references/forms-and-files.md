# 原表填写、资料命名与打包

本节使用包内模板，无需读取在线文档。所有模板及来源见[离线资料索引](sources.md)。问答和补传按 [intake.md](intake.md) 执行。国内差旅用下文填表脚本；市内交通使用[普通报销单](../assets/普通报销单.docx)，境外事前公示及预算审批分别使用对应原表，不能互相代替。

## 国内原表字段

脱敏空白 Word 模板保存在 `assets/差旅报销单.docx`，不要覆盖。表题为“差旅费报销单”；正文表格有 4 个费用行。签字和财务审核栏保留空白，打印后由相应人员实际签署。

字段依次为填表日期、部门、课题组、出差地点、实际出差起止及天数、事由、每人交通工具与五类费用、小计、合计与五种付款分配、核算账号、签字、财务复审与专项审核。部门和组名默认值需核对；填表年份不要沿用模板 2025。地点、时间及合计只填原有空位；固定文字、字体、字号、下划线、段落、行高及未填签字审核区域保持原样，不整格重排。

核算账号由组秘填写/确认；没有确认时留空并列缺项，不用“R/GZ”等项目简称冒充完整账号。表内只填写实际可报金额。超标自付金额及依据放核对明细，不能混进报销合计。

## 填表脚本

`scripts/fill_domestic_form.py` 只使用 Python 标准库，读取结构化的**已确认填写数据**，校验日期、金额、合计与付款分配，写入模板副本。确认可来自已核实材料或用户明确给出的本轮填表口径；后者需在任务核对记录中保留来源及待后审事项，不视为通用财务规则。脚本不会读取票据、计算补助资格、审批报销、生成签名或自动打包。未知金额、延期申请未覆盖、付款分配冲突等问题先处理；不通过填 0 来绕过。

```sh
python3 scripts/fill_domestic_form.py --data 本次填写数据.json --output output/差旅报销单_草稿.docx
```

上例在技能目录执行；从其他目录执行时使用相应脚本路径。Python 接口为 `fill(data, output, template=None)`，默认模板相对脚本定位；CLI 可用 `--template 模板副本.docx` 指定具有相同已验证表结构的模板，不支持任意新表。输入示例（虚构数据，用于说明字段；正式数据不得照用）：

```json
{
  "filled_on": "2026-10-23",
  "department": "智能软件研究中心",
  "group": "待填写课题组",
  "route": "北京→广东省珠海市香洲区→北京",
  "start_date": "2026-10-20",
  "end_date": "2026-10-22",
  "purpose": "示例人员赴珠海某单位针对某任务进行技术交流",
  "account": "",
  "rows": [
    {
      "traveler": "示例人员",
      "transport_mode": "高铁",
      "transport": "1000.00",
      "lodging": "800.00",
      "misc": "10.00",
      "meal": "300.00",
      "local": "240.00",
      "payment_notes": {
        "transport": "单位结算",
        "lodging": "示例代付人公务卡",
        "meal": "示例人员银行卡",
        "local": "示例人员银行卡"
      }
    }
  ],
  "payments": {"official_card": "810.00", "bank_card": "540.00", "company_transfer": "0.00", "cheque": "0.00", "cash": "0.00", "unit_settlement": "1000.00"}
}
```

- `route` 用 `→` 分隔 2 或 3 个非空节点，分别对应起点、终点，或起点、途经、终点。两节点时途经留空，不补造地点；节点内混用斜线、顿号、逗号、`->` 或换行等分隔符时拒绝猜测，不作地名数据库校验。
- `rows` 至少 1 人。原表共有 4 个费用行：每人占 1 行；有 `payment_notes` 的人员另占紧随其后的 1 行，备注写入对应费用列下方格。总占用超过 4 行时拒绝生成，按经费与行程合理分表，不覆盖其他人员。不同核算账号分表。
- `payment_notes` 为可选映射，键限 `transport`、`lodging`、`misc`、`meal`、`local`，值为已确认文字，可用 `\n` 换行。不将收款说明塞入合计；长备注生成后检查是否截断，不能通过改字体、字号或行高挤入。
- 金额必须为非负、有限、最多两位小数字符串或整数，不接收浮点数。填 0 须有明确依据，例如已确认无此费用或用户明确本轮不申报该项；未知金额不能填零。
- `payments` 的 `official_card`、`bank_card`、`company_transfer`、`cheque`、`cash` 五项必填；`unit_settlement` 可选，默认 0。费用合计＝五栏付款金额＋单位结算，无单位结算时按五栏相加。
- `unit_settlement` 大于 0 时，必须在对应费用的 `payment_notes` 中提供含“单位结算”的备注，并在核对明细逐项关联金额。单位结算不冒充公司汇款，合计不新增该标签。代付、公司汇款的实际付款人与收款对象按凭证核对；单位结算方式不表示已有结算完成回执，不重复列为个人回款。
- `account` 可空：草稿照常生成并回执提醒组秘核验。填入账号表示来自已确认资料，不由脚本验证真实性。
- 国内脚本用实际日期算首尾相含天数，达到 7 天拒绝生成。申请覆盖与连续多段累计由 Agent 另核对，脚本不能仅靠单张起止日期识别全部问题。
- 默认不覆盖输出文件；脚本校验模板结构，结构变化即停，先检查新模板字段，不对未知结构继续按行号填。
- 写入仅替换原位文本节点中的空位，保留固定标签、原表布局和样式；不自动扩大行高。合计各金额为整元时可用整数，有分角时保留两位小数，不为容纳金额改变样式。生成后回读原表字段与金额，有渲染工具再检查分页、截断和签字位置；成功回执不代表完成审批。

## 资料整理

源文 S2 文件夹示例：`姓名申请深圳出差（（历史编号或联系方式已移除）-（历史编号或联系方式已移除））技术交流`。括号是**出差申请覆盖的起止日期**，不是提交申请的日期，也不是实际差旅日期。优先沿用现有申请标题；多个延期申请另做对应关系，不擅自将实际日期替换为申请日期。

文件名按“人员＋行程方向/酒店＋材料类型＋必要序号”，例如 `某人_去程_车票支付截图.png`、`某人_回程_车票电子发票.pdf`、`某人_珠海酒店_盖章水单扫描.pdf`。这是整理建议，原文截图亦仅称“参考”，不用强制重命名用户原文件。复制后整理，保留原名映射以便追溯。

单次任务可采用：

```text
原始材料/                      保留用户原件
work/
  本次差旅信息.md              问答进度、事实来源、附件与缺件、人工待办
  费用与材料台账.csv           逐笔费用及原文件映射
  组秘包清单.json              只选核验后的报销表和适用附件
  ……                          识别、逐日补助及计算核对
output/
  姓名申请某地出差（申请起止）事项/
    差旅报销单_草稿.docx        未签字或未核验时保留草稿标识
    某人_去程_支付截图.png
    某人_回程_电子发票.pdf
    某人_酒店_住宿费发票.pdf
    某人_酒店_盖章水单扫描.pdf
    ……                         仅放本次分支实际要求的材料
  姓名申请某地出差（申请起止）事项.zip
  材料核对与待办.md             交付核对记录，位于提交包外
```

同一人员多张付款截图可合成一份“某人_付款记录.pdf/docx”，按时序列明费用对象，保留原图片和票据文件，不把 PDF 截图当电子发票原文件。财务要求原件的资料在纸质清单注明持有人、待签字/已签字状态；电子扫描不能替代酒店红章水单原件。

不要往提交包塞空白模板、源制度摘录、脚本、测试样例、技能文件、内部判断或编辑备注。用户要完整工作档案时可另出档案包，不与提交包混用。

## 组秘 ZIP 的出包条件与脚本

出差人应提供的关键电子材料须补齐，申请覆盖、费用金额及付款归属须核清，报销表须回读。未满足时保留工作底稿并追问具体缺件，不能生成组秘 ZIP。仅供填写的字段草稿或用户确认的暂定填表口径，也须完成对应材料核验后再选入组秘包。

核算账号由组秘后填、报销单线下签字、纸质原件交接及组秘后续办理列入包外的 `材料核对与待办.md`，注明由谁完成。电子签字扫描件、推送截图是否属于本次出差人必交项，按渠道和具体规则判断。境外未取得核销表等必需电子表单时仍列缺件，不能用预算审批表代替。

在 `work/组秘包清单.json` 维护出包阻塞项及选入文件。示例是已核对费用为同日往返、无住宿的虚构场景，只展示接口，实际必交附件依规则补齐。

```json
{
  "title": "测试甲申请珠海出差（20261020-20261020）技术交流",
  "blockers": [],
  "files": [
    {"source": "../output/差旅报销单_草稿.docx", "name": "差旅报销单_草稿.docx", "role": "form"},
    {"source": "../原始材料/去程付款.png", "name": "测试甲_去程_支付截图.png", "role": "attachment"},
    {"source": "../原始材料/回程付款.png", "name": "测试甲_回程_支付截图.png", "role": "attachment"},
    {"source": "../原始材料/推送记录.png", "name": "测试甲_电子票据推送记录.png", "role": "attachment"}
  ]
}
```

清单由 Agent 根据台账和适用规则填写，用户通过聊天提供材料即可。

- 顶层字段恰为 `title`、`blockers`、`files`。`title` 沿用已确认的出差申请标题。若含路径分隔符等文件名无效字符，在输出名中替换并在工作记录保留原标题映射。
- `blockers` 必填列表，写具体缺件或冲突，例如 `["测试甲 10 月 22 日回程高铁付款截图待补"]`。只有对应材料补齐并核验后才能清空。账号、线下签字等人工待办在核对记录中保留。
- 每项恰为 `source`、`name`、`role`。`source` 支持绝对路径或相对**清单所在目录**的路径。`name` 是包内单层文件名，`role` 为 `form` 或 `attachment`，至少有一份已核对的适用报销表。多人分表可列多份 `form`。
- `title` 和 `name` 支持中文，采用 Unicode NFC 规范化，拒绝目录分隔符、控制字符、系统保留文件名及 `< > : " | ? *` 等无效字符。包内重名按规范化后不区分大小写检测，补传同名文件用必要序号区分并保留来源映射。

从技能目录调用，其他位置使用脚本和任务文件的完整路径。

```sh
python3 scripts/package_reimbursement.py --manifest /本次任务/work/组秘包清单.json --output-dir /本次任务/output
```

Python 接口为 `package(manifest_path, output_dir)`，返回新 ZIP 的绝对路径。输出名为 `title.zip`，包内为 `title/选入文件名`。它只打包清单选中的文件，检查阻塞项、缺失/空文件、目录、重名及已有输出，写入临时 ZIP 后回读目录、条目数量、CRC 和原文件字节，验证成功再原子发布。发布使用同目录硬链接，需要输出文件系统支持硬链接，失败时清理临时 ZIP 并报告原因。

脚本的齐备检查依赖 Agent 如实填写清单，不能通过空 `blockers` 或给任意文件标 `form` 来跳过规则与表单核验。失败后按提示补件或修正记录再运行。已有 ZIP 保留，新版选择新的输出目录，不覆盖既有交付。

生成后解压至本次任务的 `work/解包核对/`，确认仅含选入材料，回读解压后的报销单姓名、日期、金额与付款分配，逐项关联附件。核对记录留在包外，最终提供 ZIP 可点击路径、合计、文件数和人工待办，状态写“已整理，待组秘核验”。

## 核对记录最小字段

按实际适用项目列“已具备 / 待补 / 不适用 / 待核验”，不要把没有材料的项标为不适用。

| 检查项 | 记录 |
|---|---|
| 报销表 | 文件路径、填表日期、实际行程、人员、是否已回读、视觉检查状态 |
| 费用 | 分项、每人小计、合计、付款分配；凭证覆盖、退款、超标和未定金额 |
| 电子材料 | 对应清单、文件及原件映射，电子发票原文件、支付与推送状态 |
| 纸质材料 | 申请人/组长等所需签字，酒店水单原件，线下票据及财务明细表 |
| 特殊情况 | 会议供餐/自理证明、退改签、非公务之家、代付、延期、专项、境外 |
| 包检查 | 关键电子缺件及冲突已清零，ZIP 路径、文件数、解压回读结果、未混入内部记录 |
| 下一步 | 缺什么、影响金额还是签批、由谁核验；未执行的发送/ARP 动作 |
