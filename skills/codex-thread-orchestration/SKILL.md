# Codex Thread 协作编排

## 适用场景

当用户要求把工作拆成多个阶段或子任务，并由一个主 thread 持续推进时启用本 skill。典型信号包括：创建新的 Codex thread、并行或分阶段开发、每个 thread 使用独立 branch/worktree、等待子 thread 完成后继续后续阶段，以及按依赖顺序合并或 cherry-pick。

只有一个很小且不需要隔离的改动时，不要为了形式创建子 thread。

## 主 thread 工作流

主 thread 是唯一的编排者和最终集成者，按以下顺序执行：

1. 读取仓库约束和当前状态，识别未提交的用户修改；拆解目标、产物、验收条件和依赖关系，形成可追踪的任务表或依赖图。
2. 优先使用当前环境提供的真实 Codex thread 创建、发送消息、查询状态和等待工具。创建前写明每个子 thread 的边界、输入、输出、验收命令和隔离位置；不要把“在同一对话中模拟 thread”当作等价替代。
3. 在创建子 thread 前，由主 thread 先创建独立 branch/worktree，记录绝对路径、branch、基线提交和依赖；创建时把该绝对路径明确传给子 thread。子 thread 开始写入前必须在该路径执行 `git -C <worktree> status --short --branch`，确认 cwd、branch 和基线正确，并将结果回报主 thread。主 thread 集成前再次核验该路径、branch 和 diff。没有可用隔离机制时，暂停拆分并向用户说明限制，不让多个 thread 写入同一工作目录。
4. 按依赖启动任务：无依赖的任务可以并行；有依赖的任务必须等前置任务完成、校验通过并完成集成后再启动。子 thread 完成后主动读取状态和回报，推进下一项，不等待用户提醒。
5. 逐项审阅变更，运行主 thread 的集成测试，再按依赖顺序 merge 或 cherry-pick。冲突由主 thread 处理并重新验证；不得把未审阅的子 thread 结果直接宣布完成。
6. 所有阶段和验收条件完成后，由主 thread 做最终汇报并明确完成声明；仍有失败、风险或待决策项时不得宣称完成。

## Git 与隔离安全

- 一个 branch/worktree 在任一时刻只允许一个 thread 写入；禁止多个 thread 并行直接修改同一工作分支或同一工作目录。
- 如果当前代理创建机制共享主 thread 的 cwd，不能把它当作已隔离的 worktree；只有在能显式绑定独立路径并完成启动前校验时才允许执行写入任务，否则暂停并报告隔离限制。
- 子 thread 只提交自己边界内的改动；不要修改其他 thread 的 branch/worktree，也不要替主 thread 集成。
- 集成前检查工作树、基线和 diff，保留用户已有修改。禁止 `git reset --hard`、`git checkout --`、强制清理或其他会覆盖用户修改的破坏性 Git 操作。
- 脏工作树包含用户修改时，不要擅自暂存、丢弃或重写这些文件；必要时创建独立 worktree，或向用户请求明确决策。
- merge/cherry-pick 发生冲突时，保留双方意图，定位冲突后逐项修复并运行受影响测试；无法安全判断时暂停并向用户询问。

## 决策与主动推进

主 thread 自主处理实现细节、任务排序、工具选择、重试和常规冲突解决。只有会改变需求、数据或接口契约、风险接受标准、发布范围，或涉及不可逆操作的实质性决策才询问用户；提问时给出已知事实、候选方案和影响。没有这类决策时持续推进，不把可由主 thread 判断的事项回退给用户。

## 子 thread 指令与标准回报

创建子 thread 时，明确写出任务目标、范围内和范围外文件、依赖输入、隔离 branch/worktree、验收标准、禁止事项和回报格式。要求子 thread 结束时严格包含以下四项（没有内容也写“无”）：

```text
修改的文件：
实现摘要：
已执行的校验：
尚未解决的风险：
```

子 thread 不得只报告“已完成”，不得隐瞒失败测试、未提交改动、环境限制或与其他任务的假设。主 thread 收到回报后核对实际 diff 和校验输出；缺项时要求补充，不能以不完整回报作为集成依据。

## 异常处理

- 创建 thread、worktree 或 branch 失败：保留已存在状态，记录错误；尝试不改变用户修改的替代隔离方式，仍不可行则报告并停止该分支任务。
- 子 thread 失败或超时：先查询最新状态和工作树，发送一次明确的补充或恢复指令；若仍失败，标记阻塞并评估是否可安全重派。不得伪造成功回报或跳过必需依赖。
- 校验失败：记录失败命令、关键输出和影响范围；优先在责任 thread 修复并重跑，集成前必须达到验收标准，或明确把未解决项列为阻塞风险。
- 集成冲突或基线漂移：停止相关集成，重新确认依赖和用户修改，逐项解决后再继续；无法确定语义时询问用户。
- 工具不可用：先检查当前可用工具和权限，采用等价的只读诊断；不能安全满足隔离要求时，不得降级为共享写入。

## 最终汇报与完成声明

最终汇报由主 thread 发送，至少包含：完成的阶段及依赖顺序、实际集成的 branch/commit、修改文件概览、各阶段校验结果、未解决风险或后续事项，以及是否满足用户验收标准。只有所有必需任务已集成、校验通过且没有未披露阻塞项时，才能写“已完成”；否则明确当前状态、阻塞原因和需要的下一步决策。
