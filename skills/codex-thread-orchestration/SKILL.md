# Codex Thread 协作编排

按用户要求选择起点：查进度时定位已有聊天，返回当前状态；接续已有分工时复用对应聊天。只有用户明确要求新建独立聊天时才创建。主聊天负责跟进已委派的工作，直到达到约定的交付或停点。

## 派发与隔离

1. 明确每个任务的目标、输入、产物、依赖和验收条件。只读分析给出资料范围即可；涉及代码写入时，先检查仓库规则、当前分支、基线和未提交改动。
2. 用宿主提供的 thread 工具定位或创建目标。新建时把任务说明直接放入首条指令；向已有聊天派发或追加指令须有用户对该聊天的明确授权。创建异步返回时，等到真实聊天 ID 可用再跟进；不要用待初始化的 ID 或同一聊天中的角色模拟代替独立聊天。
3. 并行写代码的聊天各用独立 branch 和 worktree，按仓库约定和宿主支持的方式绑定路径。写入前核对绝对路径、`git status --short --branch` 和 `git rev-parse HEAD`。一个工作目录同一时间只有一个写入者。无法隔离时停止该项派发，保留已创建状态，先推进可独立完成的只读工作。
4. 独立任务可并行；后续任务只等自己需要的输入通过核验。若依赖的是前一项的代码，记录后续任务实际采用的集成基线。要求执行者回报产物或修改文件、实际检查及结果、尚未解决的问题。

## 跟进与交付

- 首次派发后简报各聊天的目标、依赖和写入位置。使用带游标的事件等待获取完成、失败或需要关注的状态。没有变化时继续等待；用户查进度时返回当前快照。单次查询以回答问题为止。
- 等待超时且状态未变时继续等待。聊天报错或疑似停滞时先检查最新状态；涉及代码时再核对实际工作树。确认失败后只在已有授权内恢复或重派，避免重复启动。工具不可用时说明受影响的任务，不把未取得的结果报为完成。
- 收到回报后核对实际交付物。对要求集成的代码复核 branch、基线和 diff，按依赖顺序 merge 或 cherry-pick，运行受影响的集成检查和项目必需检查。已有结果覆盖的检查不重复跑，除非基线变化、检查失败或仍有疑点。
- 保留用户已有改动，不强制清理、覆盖或替用户暂存。常规冲突在范围内修复并验证；冲突涉及需求取舍、权限或可能覆盖用户工作时，先列明受影响内容，再请用户决定。
- 按用户要求汇报实际完成的阶段、产物、验证和阻塞。分清子聊天已交付、主聊天已集成和已发布；涉及 Git 时给出实际 branch/commit。只读跟进或仅要求派发时，到相应停点即可。
