# 指标、有效性与规范复算

依据[规范 revision 85](https://my.feishu.cn/wiki/Tv7vwpewQi5JSskAiZdcIE3Wnxb)“术语与测量边界”“采样、重复与异常处理”“容量计算”。规范决定验收口径，工具契约决定原始字段含义；两者不同必须映射与复算，不能用工具默认值改写规范。逐轮采样与汇总见 [stages](stages.md)。

## 请求成功、长度有效性和整点 PASS

1. **接口请求成功**：接口成功状态、流式协议正常结束、产生可计量有效输出且没有请求错误。HTTP 200、空输出或仅收到结束事件不足以证明成功。
2. **负载／测试有效**：实际 ISL/OSL、模板、EOS／thinking、数据和冻结条件匹配，压测端正常，阶段采样与必要证据完整。接口成功但提前 EOS、长度不符或截断不能充当标准定长有效样本；不能删去此类响应后仅用合格子集认证该点。单独聊天功能检查允许自然 EOS，不并入性能统计。
3. **整点 PASS**：测试有效、核心指标完整、各门槛与可靠性通过，并满足相应轮次／边界采样。接口成功率、Goodput 或工具 `completed` 都不等于整点 PASS，定义见 [spec-v2](spec-v2.md)。

保留原工具的 success 字段及语义。若它把长度校验也算入 success，不能直接拿它冒充规范接口成功率；只有原始 HTTP、协议、输出和错误证据足够才派生规范判定，否则标“接口成功口径不可独立复核”。任何派生结果注明测试是否有效，无效点的数值仅作诊断。

## 计时与计算

使用同一客户端单调时钟。令 `ts` 为可验证的请求发出时间，`tf/tl` 为首／末有效输出，`td` 为协议完成；`Nout` 为实际生成 token 数。分别保存请求创建、客户端排队／限流、连接／序列化、发送、响应头、首网络字节、有效输出和终态能取得的边界。`start` 不天然等于 `ts`，首字节也不等于首输出；角色、空 delta、心跳不计有效输出。thinking 与正文如何计入输出和 token 须事前冻结。

| 指标 | 规范参考计算 | 单位与限制 |
|---|---|---|
| TTFT | `tf - ts` | s；含发送后网络与服务时间，不等于 Queue 或纯 prefill |
| E2E | `tl - ts` | s；参考值取末有效输出，不把协议终止混入 |
| TPOT | `(tl - tf) / (Nout - 1)` | 内部可用 s/token，门槛表为 ms/token，明确换算；输出≤1 时 N/A |
| 协议完成／尾部 | `td - ts`／`td - tl` | s，与 E2E 分列 |
| ITL | 相邻有效流式输出事件间隔，跨请求汇总事件样本 | s 或 ms，标明；事件可能含多个 token，不等于逐 token 或 request-level TPOT |
| Queue | 服务端接收到首次调度执行的等待 | 使用服务端自己的时间差；含抢占后重排队的框架值另列，不直接等同 |
| 分位数〔本版建议〕 | 成功请求的 TTFT/TPOT；逐事件 ITL；升序第 `ceil(p×n)` 项 | nearest-rank，p=0.50/0.95/0.99；逐轮报告样本量 |
| 成功率〔本版建议〕 | 成功原始请求数／实际已发原始请求数 | 已发失败、超时、取消都保留在分母，无重试替换 |
| 总输出吞吐 | 成功请求实际生成 token 总数／正式总时长 | tok/s；失败部分输出不计主吞吐，可单列诊断 |
| 完成请求吞吐 | 成功完成请求数／同一总时长 | requests/s，明确成功完成口径；全部终态完成率需要时另列 |
| Request Goodput | 成功且逐请求目标全部满足的请求数／同一总时长 | requests/s，不以点位 P95 代替逐请求判断 |

正式总时长从本轮首个正式请求发出至全部已发请求完成、失败、超时或取消收尾，包含启动与排空，不含预热；**正式发压窗口另列**，不靠收尾凑持续发压时长。不能把单请求 tok/s 做平均当总吞吐。无请求、零分母、缺必要时间戳或 token 时填 null／N/A 并写原因。

Baseline Goodput 可用逐请求 TTFT≤3 s 且 TPOT≤60 ms/token；它不包含整点 P99、Queue、可靠性全部门槛，不能代替 PASS。Research／Heavy 的 Goodput 目标须在本轮明确，例如选对应 P95 数值作为逐请求目标时注明“本轮选定”，不能称原文另有强制默认；没有冻结目标则不报告 SLA Goodput。

## 原始证据与工具值转换

若已核实当前客户端的 `first_output_monotonic/last_output_monotonic/send_monotonic` 含义及时间基准一致，可派生规范 TTFT/E2E；保留原 `ttft_s/e2e_s` 和 `start_monotonic`。若事件时间相对 start，只有 start 与 send 均可信时才能换算。旧记录缺发送边界时不能默认 start=send，标“规范计时不可复核”，不用于该门槛 PASS。

`send_monotonic` 在某些客户端只记录发送尝试，不证明服务已收到。明确这种观测边界；无法区分请求是否实际发出时保留不确定计数，不能以更小分母美化成功率。发送前明确失败不并入已发分母，但单列压测端故障及其有效性影响。客户端等待／限流时间单列；`send-start` 可能还含序列化和连接，不能直接命名为客户端排队，更不能伪装为服务端 Queue。

按工具证据保留互斥计数，例如成功、已发非超时非取消失败、已发超时、已发取消、发送前失败、未派发；若“失败”包含超时／取消，注明子集关系，不能重复相加。诊断重试另建记录，不替换失败原请求。冒烟、tokenize、聊天、预热与正式分别保存。

## Queue、并发和监控边界

- Queue、Preemption、KV Cache 使用服务端证据；客户端 TTFT 不能减去估计 prefill 反推 Queue，不跨机器绝对时钟相减。
- 逐请求 Queue 优先；累计直方图隔离本轮窗口、预热和其他业务流量，保存桶配置及查询窗口。〔本版建议〕门槛落入无法明确判断的桶区间时标未验证，需更细数据。全局混合直方图不能代表每类负载 Queue P95。
- 同样保留 OOM／重启／不可恢复错误的来源与观测范围，缺失不补零。非核心硬件项不支持不能扩展为免检核心指标。
- 以可验证的发送／名额占用到终态区间复核实际并发。仅 start 重叠不能证明超并发；证据不足标实际并发不可核验。固定请求集合尾部在途数下降，少数幸存请求不代表标称 C 的稳态。
- 开环报告目标率、实际发送率、完成率、达标率和客户端等待；客户端限流造成低发送率不能据此认证服务可持续。
- 进程 CPU% 可超过 100%，CPU 线程、全机利用率、slot、设备核数分别解释；API 主进程的 RSS 不一定覆盖所有 worker。

复算保留原目录及历史执行源码，写入独立派生目录并记录规范 revision、复算代码版本和原始输入哈希。按三轮独立判定后再汇总，不以合并分位数抹去失败；证据一致性审计通过不等于规范通过。
